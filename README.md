# MotoScan

MotoScan is a Flutter catalog and marketplace app for motorcycles, parts, and
accessories. It includes a public browsing experience for riders and a
Firebase-backed dashboard for shop owners.

## What the app does

- **Home catalog** — browse parts, accessories, maintenance supplies, and a
  curated design gallery.
- **Search** — filter the parts library by name, category, and description.
- **Motorcycle gallery** — view 50 models / 74 variants with zoomable images and
  per-variant part lists.
- **Parts by motorcycle** — drill down by brand, model, and variant.
- **Shop tab** — public marketplace listing shop profiles, locations, products,
  prices, stock, and categories, with links to Shopee and Lazada.
- **Buy options** — show matching in-stock local shops first, then marketplaces.
- **Scan tab** — capture or upload a photo for preview. AI part recognition is
  intentionally not connected yet; the UI states this limitation.
- **Shop owner dashboard** — create and edit a shop profile, add products, edit
  product name/category/description/price/quantity/image URL, delete products,
  delete a shop, and sign out.

## Authentication model

Shop owners sign in with **Firebase Email/Password** authentication. Public
browsing does not require an account.

There is **no OTP, MFA, email-verification gate, custom-token flow, or Cloud
Functions backend** in this project. An earlier OTP prototype lived in
`functions/` but was undeployable (missing `package.json`, undefined helpers,
broken verification result handling) and was never called by the Flutter app, so
it has been removed. The Firestore OTP, rate-limit, audit, and session
collections were removed with it.

If Firebase is not configured, or the current platform is not registered in
`lib/firebase_options.dart`, the app falls back to an **in-memory demo store**:

- Shop: `MotoScan Demo Parts`
- Owner login: `demo@motoscan.test` / `demo1234`
- All demo data resets when the app restarts.

Do not use a real password in demo mode.

## Setup

```bash
flutter pub get
flutter run
```

### Firebase

1. Create or select a Firebase project.
2. Run `flutterfire configure` so `lib/firebase_options.dart` and
   `.firebaserc` point at your project.
3. In the Firebase console, enable **Authentication → Email/Password**.
4. Deploy the rules and the web build:

```bash
firebase deploy --only firestore:rules
flutter build web
firebase deploy --only hosting
```

Hosting rewrites all routes to `/index.html`, which is the correct setup for a
Flutter single-page web app.

### Firestore data model

Each shop is a single document at `shops/{ownerUid}`. Products live in a
subcollection at `shops/{ownerUid}/products/{productId}`:

```text
shops/{ownerUid}
  ownerEmailHash  string  salted SHA-256 of the account email (lowercase hex)
  ownerName       string  display name
  name            string  shop name
  location        string  city / province
  description     string  shop information

shops/{ownerUid}/products/{productId}
  id          string  matches the document ID
  name        string  product name
  category    string  product category
  description string  product information
  price       number  price in PHP
  quantity    integer stock count; zero means unavailable
  imageUrl    string  optional http(s) photo URL
```

Shop documents are public so anyone can browse the marketplace. The owner's
email address is never stored in plain text: the store writes `ownerEmailHash`
(`sha256("motoscan-owner-v1:" + lowercaseEmail)`) and looks owners up by
hashing the signed-in email the same way. The salt is an application constant,
not a server-side secret, so it prevents casual exposure but not a targeted
dictionary attack.

Rules enforce:

- public reads;
- only the authenticated owner (`request.auth.uid == ownerId`) may create,
  update, or delete their shop and its products;
- `ownerEmailHash` is a 64-character lowercase hex string;
- shop field types and lengths (`name`/`location` ≤ 120 chars,
  `description` ≤ 2000 chars);
- product field types and lengths, including a non-negative price, a
  non-negative integer quantity, and an optional http(s) image URL;
- a product document's `id` field must match its document ID.

The 500-product-per-shop limit is enforced by `ShopStore` on the client.
Firestore rules cannot count documents in a subcollection, so the limit is not
duplicated in `firestore.rules`.

`firebase.json` keeps `"indexes": []` on purpose. The only queries are an
unordered collection snapshot and a single-field equality filter on
`ownerEmailHash`; both use Firestore's automatic single-field indexes, so no
composite index is required.

No TTL policy is configured because there are no expiring OTP, rate-limit, or
session documents. If such collections are introduced later, add a Firestore TTL
policy on their expiry timestamp field.

### App Check

`FirebaseBootstrap` activates Firebase App Check after Firebase initializes,
but never lets activation failure block startup:

- web builds require `--dart-define=APPCHECK_WEB_SITE_KEY=<reCAPTCHA v3 key>`;
- release Android builds use Play Integrity and iOS builds use App Attest;
- debug builds skip enforcement unless you activate a debug provider explicitly.

`ShopStore` also listens to `authStateChanges()`, so sign-in, sign-out, and
token refreshes update the store and notify listening screens.

## Assets

Catalog images live under `assets/` and are declared in `pubspec.yaml`. The
largest images are only loaded when their screen or gallery is visible. Inline
thumbnails cap their decode size with `Image.asset(cacheWidth: ...)`, so a
768 px source is not decoded at full resolution for a 92 px tile. Keep new
images compressed and reasonably sized before adding them.
